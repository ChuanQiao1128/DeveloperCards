# 当前网络卡片的学习价值与制作耗时分析

日期：2026-11-05。范围：分析与建议；本轮没有改卡、改脚本、生成新批次或改变验收状态。

## 结论

这些卡片已提供有用的判题知识，尤其是接收方安全组、允许规则合并、双向路由和服务访问路径。但“内容正确且有题卡对应”还不能证明学习者能理解、记住并迁移到原题。当前最需要修的是少量角色条件、陌生术语与因果衔接，以及私有必答要求超出题面的问题，不需要推倒现有卡组或重新提取考点。

用户称“15张”；最近三批实际累计17张独立网络卡（5＋7＋5）。第三批另外修订1张、复用4张先修，这些不计新增。本报告按最新17张分析；更早接受的15张属于另一组。

独立教学审查的建议分布为：8张保留、4张精简或澄清表达、3张补先修或因果、2张收窄私有评分范围。这是定性改进建议，不是学习成功率，也未取代既有事实审查。

## 记忆、理解与做题分别看

| 目标 | 已有帮助 | 尚未证明或需要修正 |
| --- | --- | --- |
| 理解 | 多数卡有“谁发请求、谁接收、路径怎么走”的具体因果，可以解释选择 | NAT卡仍容易背成“public＋公有子网”；EIP、Internet Gateway需随文解释用途 |
| 记忆 | 多数卡围绕一个判断；安全组允许合并、双向路由等有清晰反例 | 新名词和旁支解释增加负担；没有延迟回忆数据，不能声称已验证记忆效果 |
| 做题 | 同一判断已绑定多道题，例如来源组与允许合并共同支撑Q55、Q282，并参与Q385、Q406 | 原题改角色、改Region或要求组合时，仍可能套错；题卡设计支撑不等于学习者独立作答 |

不设统一字数上限。当前中文正面约62—101字，背面约80—192字；用户认可示例背面约100字。最长的NAT卡值得优先整理，但字数本身不是缺陷判据。关键是学习者是否只需回忆一个结论与关键原因，而不必同时掌握多个未解释概念。

## 逐卡建议

| 当前卡片 | 建议 | 最小调整及学习意义 |
| --- | --- | --- |
| 按服务器组限制接收方访问 `role-group-boundary` | 保留 | 接收方、成员组与混合子网的范围差异构成一个完整判断；不追加提醒中的内容为必答 |
| 多安全组允许规则共同生效 `allow-union` | 保留 | “任一组允许就可通过”能解释为什么加窄规则挡不住宽规则；接受等价解释 |
| 网站与数据库入口来源 `public-web-entry` | 澄清表达 | 明确“任意IPv4访客直接连接Web入口”；避免把所有IPv4来源套到ALB后端Web |
| Web访问数据库的出站目的组 `outbound-peer-group` | 保留 | 发起方、方向与目的组是一个配置判断，不因包含两项配置文字机械拆卡 |
| 安全组与NACL的来源表达 `sg-versus-acl-source` | 保留 | 成员组与IP范围的差异清楚；首次出现NACL可随文说明为子网侧访问规则 |
| local路由与访问许可 `local-route-versus-access` | 保留 | “路已存在，是否放行另看访问规则”有因果且可迁移 |
| VPC peering用途与中转成本 `peering-purpose-and-cost` | 保留 | 两VPC直连且不需中转时，说明额外EC2中转设备为什么多余 |
| peering两端路由表 `peering-both-route-tables` | 保留 | 去程与回程是一个完整往返判断，不需拆成两张 |
| 同Region对等VPC的来源组 `same-region-peer-source` | 衔接先修 | 显式复用已有“接收方＋专用来源组”卡，不另造一套解释 |
| 跨Region互通与安全组引用 `cross-region-peer-source` | 精简表达 | 解释CIDR为地址范围；保留“路径互通不等于可引用远端组”及必要的TGW peering限制 |
| 在ALB前阻断客户端 `block-client-before-alb` | 衔接机制 | 两段连接的来源变化有用；若要声称已掌握有效NACL阻断，还需确认理解首条匹配，不能仅以读过提醒抵扣 |
| public NAT放置位置 `public-nat-placement` | 优先改善因果 | 将现有“私有EC2→public NAT→Internet Gateway”移入考点；随文解释EIP为公网地址、IGW为VPC互联网出口，合并重复内容 |
| S3网关端点绕过NAT `s3-gateway-bypass-nat` | 收窄评分 | 回忆路径改变及路由原因即可；API调用方式不变可解释，但不额外列为题面未问的必答 |
| 网关端点关联调用方路由表 `gateway-client-route-tables` | 精简表达 | 保留已经修正的“不同路由表”前提；不为回答关联范围而额外要求背默认路由优先级 |
| S3网关与接口端点费用 `s3-gateway-versus-interface-cost` | 对齐问题范围 | 当前正面比较端点费，背面又谈NAT费；应把已有NAT路径纳入问题或把费用因果放回对应路径任务，保留必要知识 |
| 桶策略不改变网络路径 `bucket-policy-not-network-path` | 收窄评分 | 题面问是否改路及原因，不把“实际创建端点并关联路由表”也列为必答 |
| VPC互访与服务端点 `vpc-peer-versus-service-endpoint` | 保留 | 远端EC2与S3/DynamoDB的访问目标差别有用；不扩展成其他连接服务大全 |

`mustAnswer`为私有制作、审查元数据，当前公共卡片导出不含这一字段。上述“收窄评分”用于防止作者和审查把学习任务越加越多，不表示客户端当前会自动按这些条目扣分。

### 两项不能为缩短而直接删除

1. **TGW peering不能提供相应安全组引用能力的边界**用于解释Q510的竞争方案。可以压缩措辞或安放到合适任务，不能直接删除后仍沿用原题支撑结论。
2. **S3请求绕过NAT的数据处理费**用于Q860的费用判断。当前问题与解释需对齐，但不能为了精简把这个必要因果整个移走。

## 对原题到底有多少帮助

既有累计题卡账本核查过14道唯一题目：

- 9题记录为判断支撑充分：Q55、Q254、Q262、Q282、Q385、Q406、Q509、Q510、Q708。
- 5题保持部分支撑：Q237、Q471、Q839、Q860、Q1016。

这不是9/14的学习者正确率，也不是17张覆盖领域1全部371题。本次教学审查另发现公开Web入口可能被套用到ALB后端；修正该条件后，应定向回看Q385/Q406等相关映射。现有支撑记录没有因此被本报告自动升级或重新验收。

代表性分析：

- **Q385**：接收方来源组、ACL不能填安全组ID等知识已在卡中，能帮助组合出正确方向；但学习者若把“Web允许所有IPv4”机械套到ALB后端，仍会选错。需要明确直接连接与经过ALB的区别。
- **Q471**：当前卡能解释S3网关端点、调用方路由表及费用方向；原题未明确同Region，另有竞争选项职责未教，仍不能认定完整覆盖。
- **Q237**：当前卡能辨析远端EC2互访与S3/DynamoDB服务路径；其他连接选项及原题未明示的地址条件仍有缺口。

如果要验证“学完能做题”，可让学习者闭卷做少量已有充分支撑的原题，再做一题改变连接角色或Region的变体；要求解释决定性原因，避免只认选项。若要验证记忆，需要隔一段时间再回忆。当前没有这些实测，不推测通过率。

## 时间到底花在哪里

三批完整任务时钟约为19.2、40.1、26.5分钟，总计约85.8分钟。批次包含不同数量的新增、修订和复用，第二批还经历实际iCloud文件不可用，不能直接用总数计算纯写卡速度。

第三批有5张新卡、1张修订，具体墙钟区间如下：

| 区间 | 分钟 |
| --- | ---: |
| 资料准备与首稿 | 6.61 |
| 首稿后补证、构包、交接至派审 | 6.86 |
| 首轮独立审查 | 5.43 |
| 审查返回至修正版本派审 | 3.02 |
| 局部复审 | 1.29 |
| 复审返回至导出检查完成 | 1.00 |
| 检查完成至记账交付 | 2.28 |
| 合计 | 26.49 |

首稿后约19.9分钟，其中审查区间约6.7分钟，其他区间约13.2分钟。这些是产物时间戳间隔，含工具、对话和等待，不能当成CPU时间或模型逐项生成耗时；首稿也尚未达到送审就绪，之后补了NAT费用依据。

**实际导出并校验脚本**三批分别只运行3.633秒、0.248秒、0.178秒，合计约4.06秒。所谓“封装慢”主要是重复组织交接、合并台账、刷新引用和收尾操作，继续优化Markdown/JSON序列化没有明显收益。

第三批首次审查输入61,946字节，目标卡快照10,525字节；局部复审输入22,897字节，目标快照3,767字节。必要规则、证据和先修确实需要上下文，但应减少重复与无关材料。字节比例不能直接换算成token或耗时收益。

## 优先采用的最小优化

1. **作者同次检查题面允许的反例。** 冻结送审前检查：两子网是否可能共用路由表？访客是直接连接还是经ALB？是否同Region？谁发起、谁接收？题面未问的补充动作是否被列为必答？把这一步合进当前作者工作，不新增模型阶段。
2. **一次冻结、一次交接。** 一个输入包只含当前目标卡、真实先修、相关原题和完整相关官方摘录；删除重复规则、旧版本与无关证据。先选准材料再冻结，不能截断必要限定或跳过事实、双语、教学与题卡支撑核查。
3. **歧义修正用固定的小交接单。** 只传发现编号、变化字段、当前版本和受影响依赖；复用未变证据及仍有效的审查记录。第三批只复审改动卡及其依赖、保留8项未受影响记录的做法应继续，压缩的是修正派审前3.02分钟的操作间隔。
4. **收尾复用现有入口，合成一个本地命令。** 将UID合并、新增/修订计数、题卡映射、报告、引用快照与计时记账串起来；先写完并校验产物，再更新权威指针。无需新建数据库或另一套工作流。本轮仅提出该优化，未实施。
5. **开工先检查必需本地文件可读。** 及早发现脚本或分类CSV被iCloud卸载，避免制作到末尾才等待文件；不因本建议移动项目或修改系统设置。

第三批真实歧义是：原题面说两子网，却未说明路由表不同；两子网可能共表，原本预设的“不都走端点”就不唯一。修正为不同路由表后，独立局部复审闭合。这次核查抓到了真实问题，不能通过取消复审来提速；应该把低成本反例检查提前。

下一批可把“首稿后非审查开销从约13.2分钟降至3—5分钟”作为待测目标；在其他区间不变时，对应约8—10分钟潜在节省，尚非实测。作者与审查仍按质量完成，不强制限时。当前没有达到端到端一分钟一张，也没有足够证据承诺这个速度。

建议顺序：先定向处理入口角色、NAT因果与两处必答外延；保留TGW和NAT费用的必要判断；随后用同样大小的一批验证交接与收尾提速。无需重新提取领域1或全库考点。
