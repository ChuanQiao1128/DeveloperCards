# 制卡提速方案：保持已认可的质量标准

2026-11-05。本轮仅分析与提出方案；不修改流程代码、卡片、接受状态、预算或生产指针。

## 结论

保持领域1第4批的卡片写法。优先把作者前的输入准备与作者后的交付接入现有入口，再缩小局部复审的无关上下文。现有导出和累计收尾已经很快，继续优化它们几乎省不出分钟。

上一批仍由主会话临时筛选主题、检索材料、编写write-candidate.py和prepare-inputs.py；作者先写好卡片，之后才运行pipeline。流程自动化主要发生在后半段。重复编写这些构包、正文装载和报告代码是可以消除的操作负担。

## 23.43分钟的实际分解

依据原task-clock时间戳；区间包含模型、工具、交接和等待，不是CPU或纯推理时间。

| 区间 | 分钟 |
| --- | ---: |
| 选题、证据与首稿就绪 | 11.21 |
| 首稿到审查请求就绪 | 0.61 |
| 首轮独立审查请求到返回 | 4.77 |
| 审查返回到局部复审请求就绪 | 1.23 |
| 局部复审请求到返回 | 2.28 |
| 局部结果返回到程序完成 | 0.25 |
| 程序完成到报告、回读与交付 | 3.08 |
| 合计 | 23.43 |

两轮审查约7.05分钟，占30%；其余约16.38分钟，占70%。其中首稿前11.21分钟没有进一步可靠的分段记录，不能全部称作检索或写作耗时，也不能假定都可消除。

实际导出/导入校验0.190秒，累计清单与索引收尾1.967秒；最后3.08分钟主要是程序外的报告、检查组织与交付，不是导出慢。

## 按收益与质量风险排序

### 1. 把输入准备接到作者之前

- 从已有领域索引和需求中沿当前知识组连续推进，按判断的条件与机制选择下一批，避免每批重新通览371题并反复换题材。不得按服务名机械归并，也不拆卡凑数量。
- 用现有入口的一次本地构包，接收已选题号、目标和证据ID，完成原题/需求装载、来源切片、UID去重与manifest生成。原始内容、偏移和历史凭证完整留在私有绑定中。
- 原生作者也实际读取这份冻结输入，然后只输出一次卡片数据；无需先把双语正文写进一段Python，再运行Python生成JSON。保持现有模型、执行通道和预算约束，不因此切换CLI或增加外部调用。
- 作者输入可复用question_context的语义视图，保留题干、全部选项、条件、必要判断、异常及相关官方原句，省去来源坐标、重复元数据和旧审查叙述。

现有构造的author-input约101.7KB，其中questions约44.6KB、originalQuestionCoverage约30.7KB；同组题目/需求的语义视图约25.4KB。但上一批CLI作者调用为0，这个构造文件并未通过CLI作者实际消费。因此它的体积不能解释全部实测耗时；关键是让下一次真实作者确实消费准备好的输入，而不是只新增一个“精简文件”。

可维护下一批所需的一小份待选材料清单，不重建全库蓝图，也不重新提取考点。材料齐全仅代表可送作者/审查，不代表AWS事实已通过。

### 2. 报告与最终回读由同一命令生成

已有closeout能生成摘要，但五卡阅读报告、逐题缺口表、计时、修复闭合及final-readback仍由主会话编写长脚本。将这些确定性内容从已有JSON直接渲染，放入当前交付入口。

交付保留完整卡片、题卡映射、必要缺口、来源与审查原件；减少重复叙述和人工拼装。程序做完当前版本校验后生成回读记录，主会话读取结果并向用户报告，无需再手写一轮相同的合并与核验逻辑。可以优先压缩最后3.08分钟及部分交接时间。

### 3. 局部复审只带完整的相关依赖

这次仅修OU卡的mustAnswer并复核Q709，输入仍为40,335字节：1张目标卡、4张上下文卡及12段官方摘录。代码原因是review_job在存在任何原题核查时，将本批所有卡加入上下文。

对于这次已知支撑关系，目标OU卡＋SCP基础卡及E05/E06/E07即可构成候选最小包，结构试算约20–23KB。这里只证明存在输入冗余，尚未证明缩包后语义等价，更不能声称体积减半就耗时减半。

实施时以该题已验证的支撑卡集合为起点，递归加入先修及全部相关证据，不能只按失败卡或作者自行挑的引用裁剪。题目、条件、判断范围变化，或完整支撑集合不明时，保留较宽上下文。全部选项与必要来源限定继续保留。

初次出5张新卡仍逐卡检查所有必选维度。修复后也保留规定的七项检查，只减少无关材料；不改成只有格式或只看差异即PASS。

## 连续制作时再提高产能

- 当前批进入独立审查后，主执行者可预取下一批原题和官方材料，利用等待时间。当前冻结输入保持不变；出现失败先处理当前批。
- 下一批的当前接受清单、去重、运行指针与最终冻结，在上一批完成后重新绑定，避免用旧库存或旧run哈希。
- 准备时间一并纳入整个连续生产的计时。提前做、藏到其他批次，不能算作节省。
- 同组自然有足够内容时，再比较5张与10张批量的“总耗时/新增接受卡数”。10张可能提高吞吐，同时延长单批等待；不得假定翻倍卡数而耗时不变，更不能强行拆卡填满10张。

这些做法只需要主执行者与必要的独立Reviewer，不增加多个并发作者。

## 质量如何约束提速

保持AGENTS第4.8节及既有门禁：

1. 每张一个有用判断，保留具体条件、因果、术语用途和实际竞争区别；必答仅对应所问。
2. 完整原题、全部选项、异常与相关官方原句可回读；缩包不得以模型摘要替代关键限定。
3. 独立完成FACT/B1/U1/R1/T1/S1/P1和必要迁移；知识卡接受、整题支撑和学习者效果分开记录。
4. 来源、正文、评分、规则、标准和递归先修变化仍使对应凭证失效；缓存与哈希不等于语义PASS。标准已确定时保持稳定，不无故每批修改。
5. 改动构包/缩包时，一次性用已有正确版与已知坏例校准：OU必答错配、路由表前提歧义仍须被发现；来源或题目缺失必须被拦截。不为每批新增一轮方法测试，也不重新审核全库。
6. 真实Linter、导入回读和当前指针检查保留；第一次失败、修正次数、全部耗时不隐藏。

## 建议的落地顺序与时间目标

先实施“统一作者前构包＋自动阅读报告/最终回读”，再做带依赖证明的局部复审缩包。继续使用原有pipeline，不新建另一套数据库或编排系统。

下一次保持5张与相同教学标准，先以**10–15分钟完成一批**为待验证目标。这个范围是改进目标，不是已测速度或交付保证；保留首轮完整审查，有真实缺陷仍须修复。一次小批次记录准备/首稿、首轮审查、返修/复审、交付四项即可，不新增复杂统计台账。

之后在连续制作授权下再试材料预取与自然10张批量，评估每张吞吐。当前首次审查已花约4.8分钟/5张，尚无证据承诺5张从准备到验收只需5分钟。用户约1分钟/张的目标继续保留，通过实测推进，不降低验收条件达标。

本次为方案分析，尚未实施。提速效果须用真实小批次、相同教学标准和完整验收计时验证，学习者记忆与作答效果继续单独记录。
