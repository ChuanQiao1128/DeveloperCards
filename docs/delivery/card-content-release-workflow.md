## 立即采用的顺序（前两步边界已确认）

1. **五张人工定稿与冻结。** 用户逐张讨论并确认正反面；聊天稿不另派作者。必要的独立核对在本步冻结前一次完成，实际检查正文、自评、完整官方依据、当前教学规则及依赖，保留一次必要定向返修及原FAIL。用户可见文案变化只重看受影响稿。通过后将最终canonical JSON、范围、来源、规则和真实审查记录绑定为内容就绪稿；只有聊天确认、尚缺有效核对记录的文件仍是草稿。正文、证据、自评或规则变化只失效受影响记录；哈希一致性不能替代语义通过。
2. **一次自动发布预检。** 复用已通过且精确绑定的冻结稿，执行下节两组机械检查。已有该冻结批次发布指令后使用现有`prepare-manual`一次完成预检与构包；未授权时保持内容就绪，不执行导入或发布，也不重复索要已有授权。预检不调用作者、Reviewer或远端服务。当前实时库存由Console在实际导入前核对，不能覆盖并发编辑。
3. **执行一次 Console 自动发布。** 载入 v2 绑定包，首次选自动保存目录，执行 **Run reviewed release**：内置基线核对与完整备份 → 导入 → 一次全量回读 → 登记已有审查 → 发布 → CDN 核验。恢复先查询，再继续同一 releaseId / actionId / 正文 / job，不创建另一批动作。
4. **保存一份完成回执。** 必须同时满足 job 成功、索引已投递、live 指针、公开 manifest、实际下载 SHA 和全部卡内容一致。复用 Console 的实际核验结果，无需例行第二次全包下载。自动保存原卡包字节与完成journal/回执；执行一次 `finalize` 完成精确归档并输出下一批基线，记录 build、变更 UID、包与审查哈希及实际耗时。手机可通过 Card pack updates 获取新版；日常不以用户逐张手机验收作为服务器发布完成条件，也不声称手机已经安装。Git 内容归档单独记录并完成正常合并；未完成时标 `pending-independent-archive`，不重发已上线内容。

现有包仍携带全部379张卡及对应精确凭证；完整机械比对自动完成。普通批次的语义核对仅覆盖变化与受影响依赖，并已在第一步冻结前完成。

## 第2步：一次自动发布预检

输入是第一步完成的冻结JSON、指定卡片范围、绑定的实际核对记录与官方依据，以及上一批已核验的卡包基线。发布构包另使用已有本批授权和已验证发布代码缓存；两者不由脚本虚构。

| 一次命令内的检查 | 内容 |
| --- | --- |
| 冻结包一致性 | 从实际待发布文件重新计算相应哈希，核对第一步记录；核对用户指定卡片的UID/顺序与实际变化，保证其余卡片正文及身份不变；检查原审查输入、响应、结果与本版正文、证据及规则的绑定，直接复用真实通过记录 |
| 发布数据格式 | 校验JSON、必填字段、英中数据结构、完整库存、预期hash/schema/revision/order及基线绑定；使用真实Console解析器精确回读，确保正文与空行保留；复用未变且通过检查的发布代码缓存 |

执行入口只有一次：

```sh
python3 tools/aws_cards/repair_release.py prepare-manual REQUEST.json OUTPUT
```

这是现有零模型、零生产写入的本地构包入口；无需新增wrapper或逐项人工执行。`repair_batch.py run --manual-patch`属于第一步的冻结前核对，不得在第二步例行重跑。哈希、范围和记录绑定是同一轮一致性检查，不扩成三轮审稿。单次运行保留读取、验证及归档之间必要的防修改核对，不以减少廉价计算为由移除这些保护。

成功以真实`preflight.json`的`EXACT_BINDINGS_VERIFIED`为准，简明报告实际changed/unchanged/total；例如“预检通过：5张变化、374张未变”。这不是已经发布成功。详细证明、真实请求/响应及文件哈希继续自动留存，无需用户逐项操作或重复确认。

失败保留实际错误和输入：格式、身份、范围或记录绑定问题定向定位并停止；涉及正文或技术事实的改动返回第一步，仅处理受影响卡及依赖。缺少/失效的记录不能自动补成PASS，不能靠重算哈希、改凭证时间或重新捕获线上基线来放行。发布包登记凭证最长24小时；真实过期时重新核对当前证据与绑定，不例行重写全部卡。完整备份、原动作恢复与当前库存并发保护继续由Console执行。

## 第3步的最终失败邮件（本轮接入范围）

沿用现有通知队列、notifier及SES；普通AI自动化保持off。`CONTENT_PUBLISH_ALERTS_SINCE`为独立启用时间，缺少/无效时不扫描；只处理该时间之后、有实际发布凭证、属于当前代次且未删除卡组的发布任务。历史失败、被替代/明确回滚的任务不补发。

触发条件为：构建明确FAILED；消息投递达到5次、仍未确认投递且租约结束；当前live构建的索引达到需人工处理状态。处理中、尚可重试、活跃租约、已经确认投递和已投递索引均不因此发邮件。SQS Worker的3次接收机会与这两个投递计数分别记录。

现有15分钟后台tick负责扫描；其AI mode为off时也可执行这项独立通知，正常Console维护入口亦可扫描。首次发现到发送之间可能等待一个tick，并非秒级推送。每轮最多5条，新建通知按任务/阶段唯一键去重，专用单飞锁覆盖已有通知补发；普通自动化重发器不处理此子类型。通知队列发送失败与插入后从未发送的记录由同一通道恢复，保留原notificationId；不重新发布卡片。

扫描SQL和发送受局部取消预算约束；发送结果确认和解锁使用独立短清理预算，避免截止时丢失补发状态或重复补发已确认消息。SQS发送结果不明标为`ENQUEUE_UNCONFIRMED`；沿同一身份恢复，邮件传输仍遵循至少一次投递语义，不承诺跨容器绝对只收一封。

邮件包含卡组、release/job/build、阶段、投递尝试次数或诊断入口；不携带原始异常堆栈、收件人地址或凭证。操作性通知不触发`automation.exception`外部webhook。通知自身发送失败仍由现有通知故障指标/死信告警兜底。

隔离PostgreSQL及捕获SQS信封用于验证真实触发、去重、取消和补发；此前Console测试邮件已在实际收件箱核实。两类证据分别记录，不把通道测试或合成发布任务称作生产发布失败演练。生产代码部署与扫描观测以本轮回执为准；后台公网核验、终态FAILED重启和恢复成功邮件仍按各自步骤验收。

## 已落实的工具与契约优化

1. **人工稿直达审查。** `repair_batch.py run ... --manual-patch PATCH.json` 接收真实聊天定稿，跳过作者调用；保留来源字节、原卡任务和一次实际独立审查。`repair_release.py prepare-manual` 核对这些真实记录并复用现有导出逻辑。单卡定向返修可携带逐字段相同的已 PASS 卡作为第二个迁移上下文，不能换掉原任务或加入未审知识。
2. **规则进入实际请求。** 作者和 Reviewer 都读取 AGENTS 第 4.0 节完整现行正文、版本与 SHA-256；新人工稿导出核对实际请求确实包含这些内容。不存在完整规则时停止，不继续用旧摘要调用模型。
3. **JSON 为真源。** Markdown 只作阅读与 Linter 输入；本地 JSON 精确回读后，最终完整发布包再交给真实 Console `parseReleaseBundle()` 校验。空行、双语和所有兼容字段保留；这不产生模型 PASS。
4. **内容与代码版本分别绑定。** 保留 v1 API 字段名 `mainSHA` 以兼容，含义明确为实际已验证的发布代码 main 提交。新的 `repair-release-v2-code-content-separated` 证据额外记录 `publisherCodeMainSHA`、关键工具文件哈希、完整 `projected-cards.json` 的 SHA 和独立 Git 归档状态。服务器原本只记录 `mainSHA`、校验格式，不查询本批内容是否已在 Git，因此无需新服务器字段或修改权限门禁。实际GitHub核对所选main、成功required checks及12个关键文件后保存`publisherCodeVerification`；构包器会消费该记录并比较本机文件SHA，缺项、失败或代码变化均阻断。只填40位字符串不构成验证。未变版本复用已有记录，代码/规则/契约变化先合并验证。
5. **完整留存实际证明。** 构包同时保存实际审查 request/response/input/output/schema/result、引用官方资料、人工稿和授权、当前候选，以及上一发布包与回执；`proof-archive.json` 逐文件绑定。保留前版证明链，未变卡按精确绑定复用；不重新审查 379 张。

6. **v2基线内置。** `expectedBaseline`绑定原live指针和全活动库存UID/hash/schema/revision/order；导入前自动检查，不再下载后人工跑第二次门禁。v1仅兼容既有冻结journal恢复。
7. **一次回读与持久证明。** 全卡回读2次降为1次，完整snapshot 6次降为3次。最终proof和真实CDN字节按owner/release/bundle保存；刷新先查原动作并核对当前job/build/live，再复验缓存字节，无需重复下载。
8. **一次选目录与统一收尾。** 支持的浏览器自动保存四份文件；owner Web Lock涵盖journal CAS及文件写入，避免旧标签逆序覆盖。其他浏览器导出一个完整文件。`finalize`先冻结原字节再校验，不重复网络或模型调用；成功目录直接作下一批基线。

启用后的默认顺序：**五张人工定稿（冻结前完成一次必要核对）→ 冻结内容就绪 → 用户“发布” → 一次自动预检/构包 → Console自动备份、导入、发布/CDN核验 → 回执及手机拉取；Git归档另行完成。** 用户明确要求本批先合并再发布时遵从其顺序。

## 系统内部的实际顺序

1. Console 持久保存完整备份和冻结动作，依次导入、回读、登记已有审查。
2. API Gateway 和后端 Lambda 验证身份、deck 权限、当前快照及未过期/未撤销收据，在 PostgreSQL 事务中保存 PENDING job、generation 与 dispatch，再提交事务。
3. API 发 SQS 消息：只有 `jobId/deckId/adminSub/note`。Worker Lambda 消费消息，重新从数据库读取并校验已审快照，生成版本化 S3 `deck.json`。
4. Worker 在事务中提交 SUCCESS、`decks.live_build_id` 与 manifest 待投递记录，再调用共享 ManifestBuilder。
5. ManifestBuilder 读取当前 live 指针，用 ETag 条件写 S3 `manifest.json`；CloudFront 提供索引和卡包。Console 实际下载比对后才记发布完成。
6. 手机通过远端索引比较版本，下载、校验并确认落盘。Home 可复验已安装免费卡包，设置页可强制检查；这是源码行为，本轮未验证设备当前 OTA 版本。

恢复：HTTP 结果不明先查原动作；dispatch 租约/退避最多 5 次。SQS 系统错误重投最多接收 3 次后 DLQ，业务校验错误 FAILED；manifest 使用独立持久恢复，可重放同任务投递索引而不新建卡包。维护恢复另受配置开关控制。以上为当前源码和 Terraform 声明，不冒称本轮核查了生产控制台配置。

代码 CI 的路径分类、push/PR 重复触发及浏览器缓存不在普通修卡中临时修改，也不通过取消仓库强制检查提速。不承诺未经下一批实测的发布时间；记录准备、审查、合并、发布、维护和总耗时，重叠阶段不相加。
