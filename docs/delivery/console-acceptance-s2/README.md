Root must never import observer/clone function resources or use a Terraform Lambda data source against these new credential-bearing functions. New S2 observer/clone secrets are absent from their tfvars, plan, outputs and state; existing project Lambda resources remain Terraform-managed and this makes no claim about their legacy state. ## Root execution binding and real acceptance remaining

The CLI remains a local boundary: it returns exit 2/UNKNOWN without root session/browser/credential callbacks. Actual SDK lifecycle entry points are now implemented in `scripts/ops/console_s2/cloud.py` and are called directly by root after independent review. `preflight --read-only` validates the local frozen manifest and checks that loopback port 5188 is free, then explicitly reports live identity/ownership/ACL as not observed. `plan-check` verifies only the exact saved plan bytes, not its allowed changes. `auth`, `drills`, and `cleanup` do **not** execute or certify cloud work. Actual OAuth/browser/incident acceptance remains a separate root execution obligation; lifecycle implementation alone cannot close AUTH/PRIV/DRILL.

Reusable primitives are implemented:

- `guards.Ledger`: locked atomic/fsync journal, immutable manifest binding/counters/clocks, durable intent **before** each create, no repeat create until response-loss reconciliation, exact returned ID plus live name/ownership tags, exact cleanup IDs. Creation calls remain root driver callbacks, never arbitrary CLI SQL/endpoint arguments.
- Deadline is min(manifest expiry, firstCreate+120m, activeStart+45m). Work stops five minutes before the deadline to reserve recovery/cleanup; injection also stops by activeStart+30m. Setup >=90m forbids opening the active window. No clock reset or retry reset.
- `guards.sdk_client`: root-supplied session only, retries `total_max_attempts=1`, one-second connect/nine-second read; every actual SDK wire send counts, including polls/pagination. Cleanup has a separate 250-SDK-call cap beyond the global 400 work-call cap in execution budget v3. The historical 250-call plan is retained; this explicit internal allowance revision is not a user-supplied spending budget. Root must additionally count Lambda/observer/collector invocations and each actual browser network request, including OAuth and reloads; top-level helper counts are insufficient.
- `observations.Http`: actual frozen isolated HTTPS API only, no redirects, bounded request/response, token in memory only, only status/times/length/SHA metadata leaves the helper. Its raw response is private caller memory and must not be dumped to evidence. Root's business paths and payload fixtures must be frozen.
- `observations.sample_expiry`: actual old signed token HTTP samples at exp-15/+15/+75 with observed intervals. `token_metadata` parses **unverified metadata only** and is never an authorization decision. Genuine Hosted UI PKCE/SDK issuance and public JWKS verification are mandatory; no test token generator exists.
- Fixed catalog SQL under `sql/` inspects effective table/function/schema/default privileges and shared dependencies. It never grants/revokes, executes production data queries, or drops anything. The root's separately reviewed `db-bootstrap/` helper owns exact operations, parameter/identifier validation and cleanup.

Root must still bind real Hosted UI A/B/App login and refresh, isolated group removal, real browser logout/switch and delayed-success/abort observations, exact isolated learner deletion, both real business incidents, CloudWatch/SNS/mail/Console observations and normal publish/rollback reconciliation. The fixed incident obligations returned by `incident_requirements()` are a guide only; checkboxes or copied receipts cannot produce PASS. No SetAlarmState, direct SNS publish, fabricated snapshots, fake authorizer claims, `page.route` mocks, modified timestamps/message age or native/OTA evidence can substitute.

Before first create root must install an **independent bounded cleanup watchdog**, register its exact resource intents, and verify its own driver is capable of all cleanup steps. `Ledger.register_cleanup()` records this fact; it does not itself install a watchdog or execute teardown. Terraform provider internals cannot be honestly accounted by the SDK wrapper. `cloud.py` supplies exact SDK creates/readbacks/teardown instead of applying the isolated scaffold. Its every actual wire send is counted, including retries/polls/pages, and every create has a durable intent and exact returned ID. The standalone IaC remains a reviewed reference, not the lifecycle execution path.

Cleanup disables the exact schedule/alarm actions, rolls back blockers in finally/watchdog, exports bounded evidence, resolves each pending creation intent by live name+tags, and only then deletes exact owned IDs, objects/versions, DB and roles. All absence readbacks/tombstones and production-baseline checks remain mandatory. No prefix-only/wildcard delete, DROP OWNED/CASCADE in production or automatic expiry guarantee exists. Host offline/crash remains incomplete until root resumes exact cleanup before other work. Production observer/alarms persist; isolated cleanup never deletes them.

The isolated core/worker `ListBucket` permission applies to the one complete isolated bucket. This matches existing missing-object HEAD/404 behavior needed for the initial manifest CAS; a `s3:prefix` condition would not be supplied by HEAD and can turn an expected 404 into 403. Object read/write remains limited to `content/*` and `premium/*`, with snapshot read separately scoped; neither core nor worker receives DeleteObject. Root cleanup alone deletes owned objects.


## Concrete SDK lifecycle (execution budget v3)

`cloud.foundation(session, ledger, frozen_manifest, root_watchdog)` creates only the exact isolated SG/five rules, core role/log group and unaliased numeric owner helper. It has no bucket/queue/content grants, no API route and no business alias. The frozen bootstrap hash/version are retained after core is upgraded. Root invokes only that numeric helper with transient owner credentials using an instrumented Lambda client; request/password never enters evidence.

`Ledger(..., phase="foundation")` requires only independently reviewed foundation proofs (owner channel, network, source/artifacts, cleanup). Unknown production/isolated ACL, schema61 and EXPLAIN remain UNKNOWN. Root then measures these with the fixed helper and uses `attest_foundation(new_frozen_manifest)` to advance only those proof fields without resetting IDs, counters or clocks. `cloud.prepare_identity(...)` requires the measured DB proofs and creates the actual passive pool/two clients/groups/domain for genuine HTTPS public JWKS acquisition and packaging. Root freezes real JWKS file SHA, exact source URL/issuer/pool and the final core ZIP containing identical public bytes under `Jwks/<pool>.json`, then calls `promote_runtime(final_frozen_manifest)`. Only prerequisite proofs, final artifacts and public JWKS fields can change across promotion.

`cloud.runtime(session, ledger, final_frozen_manifest, credential_callback)` requires all runtime proofs, verified source-manifest/saved-plan bytes, four actual package hashes, public JWKS file and core-ZIP equality before creating business infrastructure. Root's callback supplies only a fresh 40–64 ASCII alphanumeric PGPASSWORD in memory per runtime kind. The driver creates the single bucket/two queues, remaining roles/logs/functions/numeric versions and exact `test` aliases, API/real JWT authorizers/routes, eight real alarms, disabled SQS mapping and disabled 15-minute schedule. Only two alarm actions are enabled. It does not issue fake auth tokens, invoke business handlers, seed rows, publish SNS, set alarm states or enable fault injection.

`cloud.cleanup(session, ledger, final_manifest, root_db_cleanup_callback, evidence_exported=True)` has a separate 250-send reserve and default 600-second deadline (allowed range 300–900 seconds). It disables schedule/alarm actions/mapping, stops new worker execution, uses the exact preserved numeric helper for root's fixed DB teardown, deletes only live ownership-checked recorded resources, and records absence/tombstone results. Eight alarms use one exact-name delete/readback batch to stay within the reserve. Objects/versions must fit one bounded 1000-key page and 1 MiB. If Lambda ENI release prevents SG deletion, the VPC execution roles are retained so Lambda can finish release; cleanup stays INCOMPLETE. No root baseline absence result is fabricated.

Root's independent watchdog may reopen the original frozen foundation manifest with `Ledger(path, initial_manifest, phase="foundation", cleanup_only=True)`. A manifest hash explicitly retained in promotion history permits cleanup only; creation, work counters, active-window start and promotions are forbidden. Starting cleanup blocks concurrent work/creation. This keeps teardown possible after root promotes the current proof/package manifest.

Untagged provider children (pool clients/groups/domain, inline policies, API children and aliases) are identified by exact returned ID plus their live independently tagged parent ID. Individual Scheduler schedules cannot carry tags; they are bounded to their exact recorded name/ARN, tagged dedicated scheduler role and exact collector alias. These provider limitations require explicit review acceptance and are never represented as observed child tags. S3 cannot tag a general-purpose bucket atomically during CreateBucket: a create response lost before tagging remains uncertain and blocks automatic bucket deletion until root supplies an independently verified ownership resolution; other owned cleanup continues.

Driver inputs include `executionBudgetVersion="s2-execution-budget-v3"`, reviewed `sourceManifestPath/sourceSha256` and `savedPlanPath/savedPlanSha256`, plus `cloud` network IDs, SNS ARN, bootstrap artifact `{path,sha256,handler}`, database public fields `{host,productionDatabase,legacyMode,sslRootCert}`, final four artifacts `{path,sha256}`, and public JWKS `{path,sha256,poolId,issuer,sourceUrl}`. The helper handler is `ConsoleS2.DbBootstrap::ConsoleS2.DbBootstrap.Function::Handler`. Root receives `{functionName,numericVersion,manifestSha256}` for helper invocation. Source files are rehashed before each lifecycle stage; no new S2 observer/clone credential-bearing Lambda config enters Terraform.

The conservative healthy provisioning estimate is 240 isolated SDK sends, plus at least 50 incident-control sends and 100 production-control sends unless production completion is already frozen. Before any create the driver requires this amount to remain within the one global 400 instrumented-call allowance. Every actual send remains capped; propagation/response loss can still force UNKNOWN and cleanup. Historical pre-attempt metadata calls (8+ CLI commands; transport/STS/cache total UNKNOWN) remain separately reported and are not silently reset into this attempt. No AWS bill hard cap is claimed.

Offline transport tests validate every request shape against pinned botocore without constructing cloud clients. They cover the whole source lifecycle, not actual provider behavior, real authentication or notification receipt. Root must independently review this source and all exact policy/plan/ARN/phase bindings before any write.


## One targeted lifecycle repair after independent FAIL

`S2-LIFE-001` and `S2-LIFE-002` in `review/S2-lifecycle-v1.json` remain historical failed-source evidence. The repair retains the exact core numeric helper, its role/policy/log, isolated SG and RDS ingress/egress whenever the fixed DB callback cannot confirm DB/roles/blockers absent. Unrelated owned resources still clean up. The retained dependency keys are explicit tombstones; they are removed only after a later exact callback confirms absence. A successful callback result is durably bound to run ID, helper function/version and frozen helper manifest hash, so later cleanup does not need the deliberately deleted helper again. Cleanup preparation ignores absent records and marks observed provider absence successful, rather than manufacturing new failures on re-entry.

Execution budget v3 changes only the internal cleanup cap from 150 to 250 before first cloud write. The work cap remains 400 and every other resource/handler/observer/browser/time/TTL bound is unchanged. The prior 150-call plan, modeled 141-call healthy result, failed review and counters are retained as history. This is a bounded engineering allowance, not a user-specified numerical budget, and root must freeze and independently review its amendment before execution. Retry/re-entry never resets counters, clocks or manifest history.

Root's real synchronous DB/credential callbacks and independent watchdog wall-clock/cancellation/Invoke-stream behavior remain UNKNOWN until separately bound and validated before execution. Offline modeled callback Invoke calls demonstrate accounting and state transitions only; they do not establish actual timeout, cleanup exclusivity, AWS deletion, DB absence or final acceptance.


## Final bounded dependency extension (S2-LIFE-003)

The second independently reviewed counterexample separates an ownership-proof parent from a provider lifecycle parent. If schedule deletion or its absence readback remains unconfirmed, cleanup retains the exact scheduler role and inline policy and leaves the schedule active in the ledger. IAM-role deletion can never prove Scheduler schedule absence. An owned Cognito domain likewise must be confirmed absent before its pool is deleted. An inline policy not confirmed absent retains its IAM role rather than relying on a later DeleteRole conflict.

Child absence can now be inferred only for explicit native-containment pairs: HTTP API → route/authorizer/integration/stage; Lambda function → alias; Cognito pool → client/group/user; IAM role → inline policy (an inline policy cannot outlive its role). Domain → pool and IAM role → schedule are excluded. Each inferred absence records the exact provider-parent proof. Other existing edges (SG rules, queues, functions/roles and mappings) continue to require their own exact ownership/absence reads; no new deletion scope is introduced.

Offline regressions retain actual fake-provider schedule/domain state after one failed delete, then retry the same ledger after work expiry, proving no COMPLETE result while the retained resource remains. Counters and manifest/clock history accumulate across retry. This is the final bounded source repair candidate; earlier FAILs and S2-LIFE-001/002 closures remain history, budgets stay 400/250 under v3, and any further blocker must be retained and stopped for root review. Actual callbacks/watchdog bounds and real cloud behavior remain UNKNOWN.
