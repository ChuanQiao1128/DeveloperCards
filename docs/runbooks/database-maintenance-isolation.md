# Runtime / maintenance database isolation (N6)

This is a **prepared, locally tested cutover**, not evidence of a deployed role, database or Lambda version. Do not execute it during ordinary CD. Existing pre-cutover routes work until the owner chooses the explicit transition. AI automation stays off. No new function, schedule, DB, endpoint, or recurring compute is needed.

## Roles and grants

- `developercards_app`: existing runtime LOGIN, independent runtime password; no role memberships, schema/database ownership or CREATE/TEMP privilege. API and Worker share this DML capability.
- `developercards_schema`: NOLOGIN object/database/schema owner. Owns deletion barriers, immutable evidence triggers, functions and migrations.
- `developercards_migrator`: independent LOGIN/password, NOINHERIT, member of schema owner. Only the maintenance handler executes fixed `SET ROLE developercards_schema` after checking both the authenticated login and initial current role.
- Runtime SELECT/INSERT only: account_deletions, content review receipts/revocations/actions, admin_audit, ai_review_events, automation_decision_events. Schema migrations SELECT only. Other business tables have explicit DML grants in `scripts/db/isolate-runtime.sql`. Sequences permit USAGE, not SETVAL. Optional existing embedding/search functions retain non-definer extension capabilities.
- New tables/functions receive **no automatic runtime grant**. After any new migration, review its DML needs and apply precise grants as the owner; rerun local permission tests. This intentionally fails closed rather than silently granting future security tables blanket DML.

The database cutover is outside numbered migrations. It never runs through deploy.sh or normal schema updates, and transfers ownership only on an explicitly selected database. It also removes the public schema's default CREATE capability. Runtime can't SET ROLE to either maintenance principal, disable triggers, change evidence, truncate retained fences, alter schema or write the migration ledger. The retained fence is not automatically expired.

## Artifact and IAM boundaries

`src_C/package_lambda_zip.sh` builds the existing `dist/vpc.zip`; it now includes `RecallSmith.Lambda.Vpc.Db.MaintenanceFunction`. There is no second function or extra always-running service. The owner publishes an immutable version of the existing code with the maintenance handler, dedicated execution role and public PG/TLS configuration. **No maintenance password is ever placed in Lambda environment/configuration**, including temporary $LATEST and immutable versions. Each direct invocation reads the independent password from the owner's private 0600 config and sends it through a private temporary JSON file. The handler uses an invocation-local, nonpooled connection; it does not modify process environment or a shared data source. Record the reviewed source SHA, zip SHA-256, Lambda CodeSha256 and returned numeric maintenance version in the change record. Package only after all integrated source changes are frozen.

`infra/modules/identity/maintenance.tf` defines the dedicated role with the existing VPC/log capabilities, without S3, SQS, AI, parameter/secret reads, Lambda actions or role assumption. API/Worker execution roles explicitly deny Lambda configuration/code reads, version invocation, mutation, role assumption/PassRole and secret/SSM reads. The existing MFA owner retains recovery access; no new AdministratorAccess or wildcard PassRole grant is added. Ordinary deploy/CD roles explicitly cannot pass the maintenance execution role. Existing infrastructure-administration rights remain trusted infrastructure administration, not a new runtime capability.

The normal `VpcFunction` rejects all requests if `DB_ACCESS_MODE=maintenance`. The dedicated handler rejects $LATEST, aliases (including prod), HTTP-shaped payloads, invalid operations and a non-maintenance DB login. It invokes the same migration lock, destructive-confirmation, transaction, audit and SQL path as the existing migration runner; it never constructs an admin JWT. The only accepted event fields are `Operation` (default `plan`), optional `ConfirmDestructive`, and required transient `Password`; unknown/duplicate fields and HTTP events are rejected. The password is not logged or echoed in exceptions.

Ordinary deploy/CD may still read unqualified/qualified GetFunction, GetFunctionConfiguration and version lists; these reveal only public maintenance configuration. They must not read the owner file or direct invocation payload. The existing trusted owner workstation/process, MFA session, private file and direct IAM invocation transport carry the plaintext credential transiently. This design does not prove encrypted storage or protect against compromise of the owner workstation/session, Lambda service, or reviewed privileged code. Do not enable payload/debug logging; never capture request files in release evidence. The dedicated execution role has no secret-reading service permission.

`--expected-code-sha256` is mandatory with `--apply` for create/invoke. Supply the **base64 SHA-256 of the reviewed ZIP** from local frozen release evidence. Creation checks the original $LATEST, rechecks after configuration, passes the expected hash and RevisionId to publish, and verifies the returned hash. Invoke rechecks the immutable version hash before opening the private credential payload. This prevents privileged execution of arbitrary code changed by ordinary CD; pause competing deployments for restoration and alias stability. No owner credential is sent to unreviewed code.

## Protected rollback after 056

Runtime cannot bypass the live guard with `recallsmith.rollback_deck`: the bypass additionally requires `current_user` to be the decks table owner. The trigger is not SECURITY DEFINER. Only the fixed-search-path SECURITY DEFINER `content_release_rollback` performs the owner-context transition; PUBLIC execute is revoked and only the intended runtime login is granted execute during cutover. Runtime has no schema-owner membership and cannot create/replace this function.

The function locks the protected deck and validates the same-deck SUCCESS target/content hash, expected live pointer, attempted release/receipt generation and absence of a later in-flight generation. It advances the generation and fails pending work only when a real restoration is required. An already-restored confirmation preserves later pending work. It atomically writes append-only `content_rollback_actions` with the full request binding and original result; exact retries return that result and changed action payloads fail. Runtime can SELECT this audit, but cannot INSERT/UPDATE/DELETE it. Existing release action records and immutable review/deletion triggers remain. The API uses the function on 056 and preserves RequestBudget transaction cancellation.
