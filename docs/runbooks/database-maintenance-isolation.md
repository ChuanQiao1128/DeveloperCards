# Runtime / maintenance database isolation (N6)

This is a **prepared, locally tested cutover**, not evidence of a deployed role, database or Lambda version. Do not execute it during ordinary CD. Existing pre-cutover routes work until the owner chooses the explicit transition. AI automation stays off. No new function, schedule, DB, endpoint, or recurring compute is needed.

## Roles and grants

- `developercards_app`: existing runtime LOGIN, independent runtime password; no role memberships, schema/database ownership or CREATE/TEMP privilege. API and Worker share this DML capability.
- `developercards_schema`: NOLOGIN object/database/schema owner. Owns deletion barriers, immutable evidence triggers, functions and migrations.
- `developercards_migrator`: independent LOGIN/password, NOINHERIT, member of schema owner. Only the maintenance handler executes fixed `SET ROLE developercards_schema`.
- Runtime SELECT/INSERT only: account_deletions, content review receipts/revocations/actions, admin_audit, ai_review_events, automation_decision_events. Schema migrations SELECT only. Other business tables have explicit DML grants in `scripts/db/isolate-runtime.sql`. Sequences permit USAGE, not SETVAL. Optional existing embedding/search functions retain non-definer extension capabilities.
- New tables/functions receive **no automatic runtime grant**. After any new migration, review its DML needs and apply precise grants as the owner; rerun local permission tests. This intentionally fails closed rather than silently granting future security tables blanket DML.

The database cutover is outside numbered migrations. It never runs through deploy.sh or normal schema updates, and transfers ownership only on an explicitly selected database. It also removes the public schema's default CREATE capability. Runtime can't SET ROLE to either maintenance principal, disable triggers, change evidence, truncate retained fences, alter schema or write the migration ledger. The retained fence is not automatically expired.

## Artifact and IAM boundaries

`src_C/package_lambda_zip.sh` builds the existing `dist/vpc.zip`; it now includes `RecallSmith.Lambda.Vpc.Db.MaintenanceFunction`. There is no second function or extra always-running service. The owner publishes an immutable version of the existing code with the maintenance handler, dedicated execution role and independent PostgreSQL credentials. Record the reviewed source SHA, zip SHA-256, Lambda CodeSha256 and returned numeric maintenance version in the change record. Package only after all integrated source changes are frozen.

`infra/modules/identity/maintenance.tf` defines the dedicated role with the existing VPC/log capabilities, without S3, SQS, AI, parameter/secret reads, Lambda actions or role assumption. API/Worker execution roles explicitly deny Lambda configuration/code reads, version invocation, mutation, role assumption/PassRole and secret/SSM reads. The existing MFA owner retains recovery access; no new AdministratorAccess or wildcard PassRole grant is added. Ordinary deploy/CD roles explicitly cannot pass the maintenance execution role. Existing infrastructure-administration rights remain trusted infrastructure administration, not a new runtime capability.

The normal `VpcFunction` rejects all requests if `DB_ACCESS_MODE=maintenance`. The dedicated handler rejects $LATEST, aliases (including prod), HTTP-shaped payloads, invalid operations and a non-maintenance DB login. It invokes the same migration lock, destructive-confirmation, transaction, audit and SQL path as the existing migration runner; it never constructs an admin JWT. The only accepted event fields are `Operation` (default `plan`) and optional `ConfirmDestructive`.
